# Small Plan adapters

## Career Ops, study and Radar

- Career refresh reads the canonical application tracker, daily internship digest JSON and follow-up file. It uses the legacy tracker at the Career Ops root if the canonical tracker is missing. Tracker rows take precedence over duplicate digest entries. Historical follow-ups are labeled as logs, and active Career Ops next-date directives supply deadlines. Refresh emits a field allowlist with no notes, contacts, local paths, mail metadata or document contents. A missing source reports disconnected. The live Career Ops read completed and the returned snapshot was inspected through counts only.
- Course CSV requires title and due_at, with optional estimate_minutes and source_id. ICS accepts VEVENT and dated VTODO, recognizes UTC and IANA TZID, treats date-only deadlines as the end of their local day, and keeps the latest SEQUENCE for each UID in the upload. Melbourne is the default floating time zone. Ambiguous or missing wall times require an explicit offset, and repeating entries produce a clear error. Each import is limited to 500 entries and 2 MB. Course subscriptions use the same bounded public HTTP(S) downloader and parser and omit the subscription URL from returned records.
- Radar fetches bounded public RSS, Atom and GitHub search. Defaults are the Hugging Face Blog and public data-science repository search. It deduplicates by source ID and canonical URL, and reports per-source errors. Source hosts and redirects resolve to public IPs and requests pin the resolved address while preserving HTTPS hostname verification. No credentials or AI inference are involved. Tests cover bounded-source logic through mocked downloads. DNS resolution timing depends on the host resolver. Live feed availability was not exercised from this session. [GitHub REST search documentation](https://docs.github.com/en/rest/search/search)

## Apple Calendar helper

- `calendar_bridge.status()` queries authorization without prompting. `discover()` is the permission entry point. On macOS 14 or later it requests full Calendar access, with the older EventKit access method available as a fallback. The helper is a signed local app bundle with embedded Calendar usage descriptions. [Apple EventKit access documentation](https://developer.apple.com/documentation/eventkit/accessing-the-event-store)
- Sync reads only explicitly selected calendars over the inclusive Melbourne date range and excludes helper-owned calendars. Reads include event titles and dates, with calendar ID and all-day status. No attendee list, location or notes are imported.
- Jobs write only to calendars the helper previously created for the selected writable iCloud source. EventKit provides the source type and title, so iCloud detection requires both CalDAV and the exact iCloud title. The helper stores created calendar IDs in `native/.build/owned-calendars.json`. Rebuilds preserve this local ownership registry. If the registry is missing and a matching title already exists, sync reports the conflict without adopting the calendar.
- A stable EventKit URL marker identifies each planner record and stores its synced revision and remote fingerprint. Sync validates the marker and checks for Calendar-side edits before modifying or deleting an event. A retry can recover the same marker inside the search window when an event ID has not been acknowledged. If a calendar disappears or a mapped event is moved, edited or missing, the affected job reports a conflict or remains pending. The recovery search covers the job range plus 31 days on each side.
- The Calendar status response exposes pending jobs and a title/time preview for confirmable edits. The user can queue the planner version for a subsequent sync. The visible queue shows up to 100 pending jobs, with conflicts first, and reports the total pending count. Confirmation is tied to the current owned event, revision, remote fingerprint, requested operation and desired planner version. A later Calendar change observed before the write invalidates the confirmation. EventKit supplies no atomic compare-and-set operation, so the helper refreshes the event immediately before checking. Moved or missing mapped events, invalid markers, duplicate markers and events with attendees or recurrence cannot be confirmed from the planner.
- The historical overview reads saved category checks before rollout and leaves the corresponding routine counts at zero. The routine-based matrix starts on the rollout date.
- The build script uses a local compiler overlay when it finds duplicate SwiftBridging definitions in macOS Command Line Tools, without modifying the installed toolchain. It builds the app in `native/.build`; the Python wrapper surfaces build and process errors. [Upstream example of the SwiftBridging overlay](https://github.com/tobias-x/screentime-archive/blob/main/build.sh)

## Verification

- `python3 -m unittest discover -s tests -p 'test_integrations.py'` passed seven tests on Python 3.9.
- `python3 -m unittest discover -s tests -p 'test_calendar_bridge.py'` passed three tests with a fake helper subprocess.
- `native/build.sh` compiled and signed the helper on macOS 15.6.1. `codesign --verify --strict` validated the bundle.
- `native/build.sh --test` passed the native marker retry, update, delete, remote edit, revision, confirmation-token identity and DST range checks.
- The planner store and services passed 31 and 5 tests, respectively. They cover stale confirmations, changed conflicts, outbox replacement, confirmation forwarding and the legacy matrix boundary. Both export tests and all nine loopback HTTP tests passed. The loopback suite used temporary databases and sandbox approval for localhost binding.
- The real helper returned pending on a status call. The work did not prompt for Calendar access or read or write live events. The actual macOS grant, iCloud account detection, Calendar round trip and retry against a real calendar still require the authorized local trial.
